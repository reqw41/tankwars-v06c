## Гипотезы

1. Время взрыва радиусов 10/30/60 — **оценка**: замерено одно кольцо r=30 (223084 vcycles), остальные радиусы масштабируются как `t(i) = t(30)·n(i)/n(30)`, где `n(i)` — число `plot` из `ellipsePoints` с обрезкой VIEWPORT (печатает тот же `run.mjs`). Не замер каждого r отдельно.

2. Кольцо медленное, потому что каждая из четырёх симметричных точек идёт через полный `putpixel` (адрес+маска), без шага маски по дуге.

3. Знак медленный: на каждый из 8 рядов цикл по 5 столбцам шрифта со сдвигами, затем три записи плоскостей; не заливка готовым байтом глифа.

4. Очистка ~21 такт/байт×3 плоскости×8192 плюс растяжка шины; без `ldir` на 8080.

## Взрыв радиусов 10, 30, 60

Как в `explode`: кольца огня i=0..R в трёх центрах (dx = 1, −1, 0) и столько же колец стирания — **6·Σ t(i)** для i=0..R.

Из скрипта (`n(30)=172`, `t30=223084`):

```
R=10  Σn=352    vcycles=2739264   с@3МГц=0.913
R=30  Σn=2752   vcycles=21416064  с@3МГц=7.139
R=60  Σn=10592  vcycles=82426944  с@3МГц=27.476
```

Это оценка (см. «Гипотезы»). При 3 МГц и растяжке, уже заложенной в vcycles: время в секундах = vcycles / 3·10^6.

## Размер ядра

Образ **8530 Б** (`rom_end − 0100h`). Ожидание задачи — до 3,5 КБ со шрифтом и таблицами. **Не уложились.**

Почему больше: диспетчер и стенд в том же ROM; FONT 320; `barrel_tab` 182; имена/цены магазина ~350; кольцо 912; линия 857 (ветки гориз/верт/Брезенхем); экраны UI 1643; палитра 333; эллипс 32-бит. Сжатия строк и общего форматтера числа не делалось — сначала совпадение с эталоном.

## Почему цели скорости не взяты

- **Точка 272 > 250.** Три записи плоскостей и `jp` (всегда 10 тактов) на 8080; даже развёртка цвета 3 не дотягивает 8 тактов.
- **Кольцо 1297 > 120 на plot.** Plot = вызов `putpixel` на каждую выдачу `ellipsePoints` (с повторами), плюс 32-битная арифметика шага.
- **Знак 15276 > 1500.** Побитный разбор 5×7 в 8×8 вместо одного байта на ряд.
- **Очистка 692680 > 350000.** Байтовый цикл `ld (hl),a / inc l` на 24576 байт с растяжкой.

Замер не подгонялся, цели не менялись.
